# CrackCS 제품 분석과 UI/UX 개편 제안

조사일: 2026-09-06. 상태: 제안 당시 기록. 구현 결과: [UI 교체·검증](verification.md). 아래 현황과 선택지는 제안 시점 기준.

## 1. 결론

CrackCS의 중심은 **CS 질문에 자기 언어로 답하고, 부족한 개념을 확인하고, 다시 설명하는 학습**이다. 추천 포지셔닝은 “백엔드 면접에서 설명할 수 있는 지식을 만드는 문제집”이다. Java·Spring 백엔드 취업 준비생을 우선 대상으로 가정했다.

추천은 A(편집된 문제집)의 탐색 구조와 B(답변 작업실)의 풀이 구조다. C(학습 기록장)는 평가 이력이 생긴 이후의 확장 방향으로 삼는다. 세 가지 색상을 동시에 사용하는 것이 아니라, 선택한 하나의 시각 언어로 모든 화면을 통일한다.

## 2. 무엇이 만들어져 있는가

README만으로 판단하면 Phase 1 서비스처럼 보이지만, 소스와 tasks.md를 함께 확인하면 인증과 관리자 콘텐츠 운영까지 진행되어 있다.

| 영역 | 확인한 현재 상태 | 근거 |
|---|---|---|
| 문제 목록·상세 | 로그인 후 공개 문제 조회 | front/src/views/QuestionListView.vue, QuestionDetailView.vue, router/index.ts |
| 인증 | 회원가입, 로그인, 로그아웃, 세션 복구, 관리자 접근 분리 | front/src/composables/useAuth.ts, router/index.ts, auth 패키지 |
| 콘텐츠 운영 | 분류·개념, 지식 문서, 문제, 회원 관리 화면 | front/src/views/admin/ |
| 근거 문서 | 출처·기술 버전·검수·공개·새 버전 도메인 | content/knowledge/domain/KnowledgeDocument.java |
| 답변 제출·이력 | 계획 단계, 현재 상세 화면에는 입력 폼 없음 | docs/planning/tasks.md FR-ANSWER 항목, QuestionDetailView.vue |
| 평가·추천·개념별 상태 | 계획 단계 | docs/planning/tasks.md FR-EVAL, FR-KNOWLEDGE, FR-FOLLOWUP 항목 |

실제 실행 화면의 사용성 실험을 수행한 것은 아니다. 이 진단은 소스, 스타일, 라우팅, API 호출과 명세를 교차 확인한 결과다.

```text
현재 학습자 흐름
로그인 → 공개 문제 목록 → 문제 읽기 → 다음 행동 없음

제품이 목표로 하는 흐름
문제 선택 → 서술형 답변 → 근거 기반 평가 → 부족한 개념 확인
                                              ↓
                              후속 질문 / 다음 문제 → 재학습

운영자 흐름
분류·개념 → 근거 문서 검수·공개 → 문제와 평가 기준 공개
```

중요한 자산은 단순 문제 개수가 아니라 검수한 근거 문서, 개념 체계, 평가 이력을 연결하려는 구조다. 화면을 전면 개편하더라도 이 도메인 구조와 기존 인증 계약을 버릴 이유는 없다.

## 3. 현재 UX의 문제와 원인

| 관찰 | 사용자에게 생기는 문제 | 개편 방향 |
|---|---|---|
| 목록 상단에 큰 소개 문구, 카드 최소 높이 260px | 반복 방문 시 실제 질문 탐색에 앞서 장식 영역을 지나야 함 | 소개는 짧게, 목록은 행 중심으로 |
| fetchQuestions가 size=20으로 첫 페이지만 조회 | 21번째 이후 문제에 접근할 UI가 없음 | 서버 페이지 정보에 맞는 페이지 이동 |
| questions.length를 문제 수로 표시 | 전체 문제 수와 현재 페이지 건수를 혼동할 수 있음 | totalElements를 전체 수로 표시 |
| 화면에 주제·난이도 필터가 없음 | 필요한 질문을 찾을 때 모두 훑어야 함 | 기존 API 계약을 확인해 필터 연결 |
| 상세 화면은 본문과 생각 가이드만 제공 | 답변을 남기고 피드백 받는 가치가 아직 전달되지 않음 | 답변 기능 단계에서 작성·제출·결과를 연결 |
| 문제 화면까지 로그인 필요 | 신규 사용자가 가치를 확인하기 전에 가입을 결정 | 공개 샘플 체험을 별도 제품 결정으로 검토 |
| 관리자 메뉴에 Topic, Knowledge Document 등 구현 명칭 | 운영자가 업무 명칭으로 이해하기 어려움 | 분류와 개념 / 근거 문서 / 문제 / 회원 |
| 관리자 사이드바에 서버 권한 검사 설명 | 업무 행동과 관계없는 정보가 주의를 차지 | 실제 상태·작업 안내로 대체 |

색상만 바꿔도 마지막 행동이 없는 문제는 해결되지 않는다. 반대로 첫 개편에 추천·채점·학습 기록을 모두 가짜 데이터로 서비스 화면에 넣으면 완성도를 잘못 전달하게 된다. 시안에서는 미래 흐름을 보여주되 실제 배포에서는 구현된 기능만 노출해야 한다.

이 영역이 빈 시장이라고 단정할 수 없다. 개인 피드백을 제공하는 경쟁 사례가 이미 있다. 차별성은 **한국어 CS·Java/Spring 콘텐츠의 품질, 판정 근거, 개념 단위 기록의 유용성**을 함께 구현했을 때 검증할 가설이다.

### 시장 진입과 사업 검증 제안

- 첫 범위: 백엔드 취업 준비생의 CS·Java·Spring 핵심 서술 문제. 전 개발 직군으로 넓히는 것은 뒤로 미룬다.
- 첫 약속: “어디까지 이해했고 무엇을 빠뜨렸는지 알 수 있다.” 합격이나 실력 상승을 보장하지 않는다.
- 유입 가설: 주제별 공개 샘플과 문제 예시가 제품 이해를 돕는다. 현재 인증 정책을 변경해야 하므로 별도 결정이 필요하다.
- 재방문 가설: 누적 점수보다 지난번에 빠뜨린 개념을 다시 설명해 보는 행동이 재방문 이유가 된다.
- 결제 가설: 검증된 상세 피드백과 기록에 대한 지불 의향을 확인한 뒤 검토한다. 아직 가격을 정할 근거는 없다.
- 운영 부담: 문제 검수, 문서 버전 관리, 잘못된 판정 대응, 평가 비용. 특히 근거가 있는 평가가 실제로 정확한지는 별도 검증이 필요하다.

이미지 검토에서 발견한 구현 시 보정 사항: A의 ‘학습 노트’ 안내는 별도 노트 기능을 추가하자는 결정이 아니므로 첫 구현에서는 제거한다. A 이미지의 ‘보통/어려움’은 현재 API 레이블인 ‘기본/중급/심화’로 통일한다. 로그인 상태와 메뉴도 실제 라우팅 정책에 맞춘다. 페이지 이동과 전체 건수는 이미지에 생략되었지만 구현 요구사항에 포함한다.

### A. 편집된 문제집 — 추천 기반

흰색에 가까운 배경, 짙은 잉크색 글자, 녹색 한 가지 강조. 책의 목차처럼 가는 구분선과 질문 제목의 위계로 읽게 한다. 과도한 종이 질감이나 장식용 세리프는 쓰지 않는다.

```text
crackCS                   문제집  학습 기록       계정
────────────────────────────────────────────────────
주제              어떤 개념부터 풀어볼까요?
전체 질문         난이도 필터                   전체 건수
운영체제          01 프로세스와 스레드 ...     기본  →
네트워크          02 TCP 전송 보장 ...         중급  →
데이터베이스      03 인덱스 ...                중급  →
Java              ───────────────────────────────────
Spring                              이전  1 2 3  다음
```

장점: 탐색이 빠르고, 콘텐츠가 적어도 자연스럽고, 현재 API와 화면을 개선하는 데 적합하다. 약점: 풀이 경험이 연결되지 않으면 단순 자료실로 인식될 수 있다.

### B. 답변 작업실 — 핵심 학습 화면

차콜 내비게이션, 흰 작성면, 절제된 청색 강조. 데스크톱에서는 문제와 답변을 나란히 두고, 모바일에서는 문제 다음에 입력란을 배치한다. 채팅 UI나 코드 실행기처럼 보이게 하지 않는다.

```text
목록으로    운영체제 / 기본
───────────────────────────────────────
질문·상황 설명       │ 내 답변
                    │ [서술형 작성 공간]
                    │          답변 제출
───────────────────────────────────────
제출 후: 이해한 부분 / 보완할 부분 / 판정 근거
```

장점: 사용자의 주 행동이 분명하다. 약점: 답변 저장과 비동기 평가가 없으면 정적인 시연에 그친다. 제출 전에 모범 답안·필수 평가 개념·가중치를 노출하지 않는다. B 이미지의 결과 영역은 제출 이후 상태를 보여주는 별도 예시다.

### C. 학습 기록장 — 재방문 화면

옅은 회색과 아이보리, 먹색 글자, 짙은 적갈색 강조. 거대한 지식 그래프 대신 읽을 수 있는 표를 쓴다. 개념마다 상태와 판단 이유, 다음 행동을 한 행에서 확인한다.

장점: 축적되는 개인적 가치를 보여 준다. 약점: 신규 사용자에게 기록이 없으므로 첫 화면으로 쓰기 어렵다. 처음에는 “아직 평가 전”과 첫 문제를 안내한다. 점수 0으로 채우지 않는다. 학습 상태 임계값은 아직 명세상 결정이 필요하며 디자인이 이를 임의 확정하면 안 된다.

## 6. 추천 화면 체계와 설계 원칙

하나의 스타일로 문제집 → 작성 → 결과 → 기록을 연결한다. A의 시각 언어를 기준으로 B와 C의 정보 구조를 흡수하는 방식을 권한다.

| 화면 | 첫 번째 행동 | 중요한 내용 |
|---|---|---|
| 문제집 | 질문 고르기 | 주제, 난이도, 질문, 실제 전체 건수, 페이지 이동 |
| 문제 풀이 | 답변 쓰기·제출 | 질문, 입력 규칙, 작성 내용, 저장·제출 상태 |
| 평가 결과 | 보완점 확인 | 판정, 맞게 설명한 개념, 누락·오개념, 출처 |
| 개념별 기록 | 다음 질문 고르기 | 미평가/학습 중/안정 상태와 최근 평가 근거 |
| 답변 이력 | 과거 답변 다시 보기 | 문제, 제출 시각, 평가 상태와 당시 근거 |
| 운영 | 검수·공개할 콘텐츠 선택 | 상태 필터, 목록, 편집, 검수와 공개 조건 |

### AI 제품의 상투적인 인상을 피하는 방법

- 실제 질문을 앞에 둔다. 추상적인 “당신의 잠재력을 깨우세요” 같은 문구는 쓰지 않는다.
- 보라색 그라데이션, 발광 구체, 반짝이 아이콘, 로봇 아바타, 장식용 차트는 쓰지 않는다.
- 모든 정보를 둥근 카드에 넣지 않는다. 목록은 행, 서술은 문단, 기록은 표로 표현한다.
- 강한 색은 주 행동과 상태에만 쓴다. 회색 글자가 읽히는지 실제 대비를 검사한다.
- AI 사용 사실을 숨기지는 않는다. 평가 화면에 자동 평가임을 짧게 알리고 근거와 불확실성을 보여 준다.
- 임의의 숙련도, 연속 학습일, 추천 이유, 자동 저장 표시를 만들지 않는다. 실제 데이터와 기능이 있을 때만 표시한다.
- “50점”만 크게 보여주기보다 “메모리 공유는 설명했지만 동기화 설명이 빠졌습니다”처럼 다음 행동에 도움이 되는 피드백을 앞에 둔다. 판정 규칙은 서버의 값을 따른다.

### 화면 크기와 접근성

- 모바일: 주제 메뉴를 간결한 선택 UI로, 표를 읽을 수 있는 한 열 목록으로 변경한다.
- 작성 화면: 모바일 키보드가 입력과 제출 동작을 가리지 않도록 검증한다.
- 본문은 충분한 글자 크기·행간을 확보하고 긴 문장은 넓이를 제한한다.
- 키보드 포커스가 보이고, 필터에 레이블이 있고, 상태는 글자와 아이콘을 함께 사용한다.
- 대기·오류 알림은 보조 기술에서도 전달되게 하며 작은 화면과 긴 한국어 제목을 검증한다.

## 7. 상태와 책임

```text
화면: 작성 내용, 필터 선택, 표시할 진행 상태
  ↓ 명시적인 요청
Service: 권한·저장·평가 호출의 조정
  ↓
도메인: 공개 조건, 답변·평가 불변식, 유효한 상태 전이
  ↓
Repository: 저장과 조회
```

디자인이 바뀌면 표시 컴포넌트가 바뀌어야 한다. 평가 규칙이 바뀌면 해당 규칙을 소유한 도메인/정책이 바뀌어야 한다. CSS나 화면 문구가 정오 판정의 기준을 결정하면 안 된다.

| 상태 | 화면의 반응 |
|---|---|
| 문제 로딩/빈 목록/조회 실패 | 각각 구분해 표시, 실패 시 다시 불러오기 |
| 필터 결과 없음 | 조건에 맞는 문제가 없다고 설명하고 필터 해제 제공 |
| 제출 중 | 중복 조작 차단, 입력 내용을 보존 |
| 응답 유실 | 멱등성 식별자로 같은 제출 확인, 무조건 새 답변 생성 금지 |
| EVALUATING | 저장된 답변과 평가 진행을 구분해서 안내 |
| FAILED | 답변 저장 여부를 실제 상태에 맞게 안내, 오답으로 취급하지 않음 |
| NEEDS_REVIEW | 판정 보류 안내, 이해 상태에 반영하지 않음 |
| 유효한 평가 완료 | 개념별 피드백과 근거, 후속 행동 제공 |
| 신규 사용자 | 평가 전으로 표시, 0점이나 취약으로 오인시키지 않음 |

## 8. 구현 순서와 검증

1. **현 기능 개편:** 공통 스타일, 로그인·회원가입, 문제 목록·상세, 관리자 화면. 페이지 이동과 필터 연결은 TDD로 별도 검증한다.
2. **학습 기능 연결:** 답변 저장·제출·대기·실패·결과. 서버 계약과 함께 구현한다.
3. **학습 기록:** 개념별 상태·답변 이력·후속 질문·추천. 실제 누적 데이터와 임계값이 준비된 뒤 노출한다.

생산 코드를 바꾸는 단계에서는 저장소 TDD 순서를 따른다. 페이지 이동 요구를 실패 테스트로 보여준 뒤 구현하고, 관련 테스트와 가능한 전체 테스트를 실행한다. 디자인을 구실로 인증·CSRF·관리자 검수 규칙을 약화하지 않는다.

첫 사용자 검증에서는 질문 찾기, 설명 작성, 보완점 찾기, 다음 문제 선택이라는 네 과제를 관찰한다. 측정 항목은 첫 답변 제출률, 제출까지 걸리는 시간, 피드백 이해 여부, 후속 문제 진입률, 재방문과 판정 오류다. 현재 기준값이 없으므로 개선율이나 성공 수치를 제시하지 않는다.

## 9. 이번 작업의 검증 범위

- 확인: 제품 명세, 작업 체크리스트, Vue 목록·상세·인증·관리자 구조, 스타일, 질문 API 호출, 근거 문서 도메인, 공개 경쟁 자료.
- 산출물: 제품/시장 분석, 서로 다른 세 가지 시안, 추천 화면 체계, 단계별 구현 범위.
- 자동 테스트: 이번에는 생산 코드 변경이 없어 0개 실행. 기존 테스트가 통과했다고 주장하지 않는다.
- 미검증: 실제 사용자 사용성, 모바일 동작, 색 대비 수치, 유료 경쟁 기능, 시장 규모, 지불 의향, AI 평가 품질.
- 기존 사용자 수정 파일은 보존했다. 실제 UI 교체와 기능 구현은 아직 수행하지 않았다.
