# CrackCS 콘텐츠·AI 운영 정책

## 1. 운영 원칙

1. 모든 문제는 서술형 주관식이다.
2. 문제와 평가 기준은 관리자 검수를 통과해야 한다.
3. AI가 만든 결과는 초안 또는 판정 도구이며, 지식의 원천이 아니다.
4. AI 평가는 공개된 KnowledgeDocument만 근거로 사용한다.
5. 초기 평가는 표현력보다 핵심 개념의 정오 판정에 집중한다.
6. CS 기초 문서는 장기 재사용하고, Java·Spring·JPA 문서는 기술 버전을 명시한다.

## 2. 문제 공급 방식 트레이드오프

| 방식 | 장점 | 단점 | 적합한 시점 |
|---|---|---|---|
| 관리자 직접 등록 | 품질과 범위를 통제하기 쉽고 책임 소재가 분명함 | 문제 수 증가가 느리고 운영자가 병목이 됨 | 초기 운영 |
| AI 자동 생성·자동 공개 | 많은 문제를 빠르고 저렴하게 확보 | 사실 오류, 중복, 애매한 질문과 잘못된 평가 기준이 함께 생성될 수 있음 | 권장하지 않음 |
| AI 초안 + 관리자 승인 | 생성 속도와 품질 통제를 절충 | 관리자 검수 비용은 계속 필요 | 정답 판정 품질이 안정된 이후 |
| 사용자 문제 게시 | 현업 사례와 다양한 관점 확보 | 표절, 저작권, 중복, 악성 콘텐츠와 검수 비용 발생 | 커뮤니티 규모가 생긴 이후 |

### 권장 단계

```text
1단계: 관리자 문제 은행
  관리자가 문제·모범 답안·필수 Concept을 직접 등록하고 공개
             │
             ▼
2단계: AI 초안 생성
  AI는 DRAFT만 생성하고 관리자가 검수한 뒤 공개
             │
             ▼
3단계: 사용자 문제 제안
  사용자는 제출만 하고 관리자 승인 전에는 공개하지 않음
```

초기에는 관리자 방식이 느리더라도 평가의 기준점이 되는 고품질 문제 세트가 먼저 필요하다. 문제와 평가 기준을 AI가 동시에 만들고 AI가 다시 채점하면 오류를 발견할 독립 기준이 사라진다.

따라서 필수 범위는 **관리자 문제 은행**으로 시작한다. AI 초안과 사용자 제출은 [추가 확장 기능](./extension-features.md)으로 둔다.

## 3. AI 모델 트레이드오프

### 3.1 모델에 필요한 능력

- 한국어 서술형 답변 이해
- QuestionConcept와 근거 문서를 이용한 정오 판정
- 오개념과 단순 누락 구분
- 정해진 JSON 스키마 출력
- 짧은 답변을 반복 처리할 수 있는 비용과 지연

모델 지식만으로 채점하지 않고 Retrieval 근거를 제공하므로, 가장 큰 모델을 항상 사용할 필요는 없다. 반대로 작은 모델이 문장을 자연스럽게 만든다는 이유만으로 정확한 채점기라고 가정해서도 안 된다.

### 3.2 OpenAI 모델 비교

OpenAI 공식 문서의 현재 GPT-5.6 계열 비교는 다음과 같다. 가격은 100만 토큰당 API 정가이며 변경될 수 있다.

| 모델 | 공식 포지션 | 입력/출력 가격 | 이 서비스에서의 트레이드오프 |
|---|---|---:|---|
| `gpt-5.6-sol` | 복잡한 추론·코딩용 플래그십 | $4 / $20 | 가장 어려운 답안과 기준 평가에 유리하지만 기본 평가에 쓰면 비용·지연이 커질 수 있음 |
| `gpt-5.6-terra` | 지능과 비용의 균형 | $2 / $12 | 정오 판정 품질과 운영비의 균형점으로 초기 기본 평가에 적합 |
| `gpt-5.6-luna` | 비용 민감·대량 처리 | $0.20 / $1.20 | 매우 저렴하지만 미묘한 오개념 판정은 자체 평가 세트로 검증한 뒤 사용해야 함 |

세 모델 모두 Responses API와 Structured Outputs를 지원한다. 출처: [OpenAI 모델 목록](https://developers.openai.com/api/docs/models), [OpenAI 모델 비교](https://developers.openai.com/api/docs/models/compare).

### 3.3 권장 모델 운영안

```text
초기 기본 평가
  gpt-5.6-terra + Structured Outputs
              │
              ├─ 판정 확신이 낮음 ──▶ NEEDS_REVIEW
              │
              └─ 운영 품질 검증용 ──▶ gpt-5.6-sol 결과와 표본 비교

비용 최적화 단계
  gpt-5.6-luna가 동일 평가 세트를 통과할 때만 일부 트래픽 전환
```

권장 시작점은 `gpt-5.6-terra`이다. `gpt-5.6-sol`은 운영 요청마다 재호출하는 자동 심판보다, 골든 평가 세트 작성과 애매한 사례의 내부 검토에 우선 사용한다. `gpt-5.6-luna` 전환 여부는 가격만으로 정하지 않고 실제 CrackCS 답변 세트의 판정 일치율로 결정한다.

모델명은 코드에 고정하지 않고 설정으로 관리하며, Evaluation에 `model_name`, `evaluator_version`을 저장한다. 제공자를 바꾸더라도 `AnswerEvaluationService`의 입력과 출력 계약은 유지한다.

### 3.4 Retrieval 임베딩 모델

OpenAI의 `text-embedding-3-small`은 검색·추천 등에 사용하는 소형 임베딩 모델이며 100만 입력 토큰당 $0.02이다. `text-embedding-3-large`는 $0.13이다. 출처: [OpenAI text-embedding-3-small](https://developers.openai.com/api/docs/models/text-embedding-3-small).

초기 문서량이 작고 Topic·Concept로 먼저 후보를 줄일 수 있으므로 `text-embedding-3-small`로 시작한다. 한국어 기술 용어 검색 누락률이 허용 기준을 넘을 때만 large 모델을 비교한다. 이는 가격이 아니라 실제 검색 정답 세트의 Recall@K로 결정한다.

## 4. 지식 문서를 한 번 저장해 계속 사용할 수 있는가?

결론은 **기초 CS는 대부분 가능하지만, 영구 무검수는 불가능하다**이다.

```text
장기 안정 지식
자료구조, 운영체제 원리, TCP 기본, 트랜잭션 원리
  → 내부 표준 문서로 정리해 장기 재사용
  → 오류 신고 또는 정기 점검 때 갱신

버전 의존 지식
Java 문법/API, Spring 동작, Spring Boot 설정, JPA 스펙
  → Java 21, Spring Boot 4.1.x, Spring Framework 7.0.x,
    Jakarta Persistence 3.2처럼 범위 명시
  → 기준 버전 변경 시 새 문서 버전 생성
```

기초 CS도 설명이 틀릴 수 있고 보안·프로토콜 권고가 바뀔 수 있으므로 “한 번 저장 후 방치”가 아니라 “한 번 정리한 표준 지식을 검수 비용을 낮춰 재사용”하는 방식이 적절하다.

## 5. 지식 문서 출처

### 5.1 출처 우선순위

| 등급 | 출처 | 사용 정책 |
|---|---|---|
| A | 언어·프로토콜·플랫폼 공식 명세 | 사실 판정의 최우선 근거 |
| B | 공식 프레임워크 Reference/Javadoc | 해당 버전의 사용법과 동작 근거 |
| C | 신뢰할 수 있는 교재·대학 강의 자료 | 기초 CS 설명을 교차 검증하는 보조 근거 |
| D | 기술 블로그·Q&A·AI 생성문 | 아이디어 탐색에만 사용하고 단독 평가 근거로 사용하지 않음 |

### 5.2 초기 기술별 권장 출처

| 영역 | 1차 출처 | 저장 방식 |
|---|---|---|
| Java | [Oracle Java SE 문서](https://docs.oracle.com/en/java/javase/)와 해당 버전 JLS/Javadoc | Java 버전별 내부 요약 |
| Spring Framework | [Spring Framework 공식 Reference](https://docs.spring.io/spring-framework/reference/) | Framework 버전 명시 |
| Spring Boot | [Spring Boot 공식 Reference](https://docs.spring.io/spring-boot/reference/) | Boot 버전 명시 |
| JPA | [Jakarta Persistence 공식 명세](https://jakarta.ee/specifications/persistence/) | Persistence 버전 명시 |
| 네트워크 | IETF/RFC 원문과 검수된 교재 | RFC 번호와 내부 요약 연결 |
| 운영체제·자료구조·컴퓨터 구조·DB 기초 | 신뢰 교재 또는 공개 대학 자료 두 개 이상 | 원문 복사 대신 관리자 작성 표준 요약 |

공식 문서에도 여러 안정 버전이 동시에 존재한다. 예를 들어 Oracle은 여러 Java SE 버전을, Spring은 여러 안정 버전을, Jakarta Persistence는 여러 명세 버전을 함께 제공한다. 그러므로 KnowledgeDocument의 `technology_version`을 생략하면 같은 질문에 서로 다른 시대의 답이 섞일 수 있다.

### 5.3 저작권 원칙

- 외부 교재나 강의 자료의 원문을 그대로 DB에 복제하지 않는다.
- 필요한 사실을 관리자가 자기 문장으로 요약하고 출처 위치를 기록한다.
- 직접 인용이 필요하면 최소 범위만 사용하고 라이선스·인용 조건을 기록한다.
- AI가 생성한 요약만으로 PUBLISHED 상태를 만들지 않는다.

## 6. 문서 검수 방법

```text
출처 등록
   ↓
관리자가 Concept 단위로 내부 표준 설명 작성
   ↓
공식 문서 또는 신뢰 출처와 문장별 사실 확인
   ↓
적용 기술 버전·출처 URL·라이선스 기록
   ↓
질문과 평가 기준을 이용한 시험 평가
   ↓
관리자 승인
   ↓
PUBLISHED → Retrieval 사용
```

### 검수 체크리스트

- [ ] 하나의 문서가 너무 많은 Concept을 섞지 않았는가?
- [ ] 각 핵심 주장에 출처가 있는가?
- [ ] 기술 버전이 필요한 문서에 적용 버전이 적혀 있는가?
- [ ] 모범 답안과 필수 Concept이 문서 근거와 일치하는가?
- [ ] 반례 또는 버전별 예외를 일반 법칙처럼 쓰지 않았는가?
- [ ] 원문 복제로 인한 저작권 문제가 없는가?
- [ ] 오답·부분 정답 예시로 AI 판정을 시험했는가?

### 재검수 주기

- 안정적인 CS 기초: 연 1회 가벼운 점검 + 오류 신고 시 즉시 점검
- Java·Spring·JPA: 기준 버전 변경 시 재검수 + 반기 1회 링크·지원 상태 점검
- 보안 또는 운영 권고: 관련 공식 권고 변경 시 즉시 점검

기존 문서를 덮어쓰지 않고 `document_version`을 올린다. 과거 Evaluation은 당시 사용한 KnowledgeChunk와 문서 버전을 계속 참조해야 한다.

## 7. 정오 판정과 난이도 정책

### 정오 판정

| 판정 | 조건 | Knowledge State 반영값 |
|---|---|---:|
| CORRECT | 모든 필수 Concept이 맞고 치명적 오개념이 없음 | 100 |
| PARTIALLY_CORRECT | 핵심 방향은 맞지만 필수 Concept 일부 누락 | 50 |
| INCORRECT | 핵심 Concept이 틀리거나 질문에 답하지 못함 | 0 |
| NEEDS_REVIEW | 근거 부족 또는 AI 판정 불확실 | 반영하지 않음 |

문장 길이, 전문 용어 수, 표현의 화려함은 정오 판정보다 낮은 우선순위를 가진다.

### 난이도

- 초기에는 관리자가 `BASIC`, `INTERMEDIATE`, `ADVANCED`를 지정한다.
- 난이도 자동 계산과 사용자별 자동 조절은 하지 않는다.
- 실제 정답률이 쌓이면 “관리자 난이도와 실제 정답률의 차이”를 분석한 뒤 자동 조절을 검토한다.

## 8. 현재 선택 요약

| 항목 | 현재 선택 | 나중에 검토 |
|---|---|---|
| 문제 형식 | 관리자 검수 서술형 | 객관식, 코드 문제 |
| 문제 공급 | 관리자 직접 등록 | AI 초안, 사용자 제출 |
| 기본 평가 모델 | GPT-5.6 Terra 후보 | Luna 비용 최적화, Sol 제한 사용 |
| Retrieval | 승인 문서 + 소형 임베딩 후보 | 검색 품질 부족 시 대형 임베딩 |
| 지식 보관 | 내부 표준 문서와 버전 기록 | 외부 동기화 자동화 |
| 평가 | 정오 판정 우선 | 표현력, 면접 전달력 평가 |
