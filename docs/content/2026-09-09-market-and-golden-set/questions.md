## CS-01 · 프로세스와 스레드

- 분야: CS · 난이도: BASIC · 우선순위: P0
- 적용 조건: 운영체제 일반; 스레드 지원 OS

**질문**

같은 프로세스의 두 스레드가 공유하는 자원과 각자 갖는 실행 상태를 설명하세요.

**모범 답안**

프로세스의 주소 공간에 속하는 코드·힙 등을 같은 프로세스의 스레드가 공유한다. 각 스레드는 자신의 프로그램 카운터·레지스터 실행 상태와 스택을 갖는다. 스택은 논리적으로 개별이지만 같은 주소 공간의 접근 권한 격리는 아니다.

**필수 평가 기준**

- `CS-01-C1` · 가중치 0.50 · 프로세스의 주소 공간에 속하는 코드·힙 등을 같은 프로세스의 스레드가 공유한다.
- `CS-01-C2` · 가중치 0.50 · 각 스레드는 자신의 프로그램 카운터·레지스터 실행 상태와 스택을 갖는다. 스택은 논리적으로 개별이지만 같은 주소 공간의 접근 권한 격리는 아니다.

**판정 사례**

- `CS-01-G01` · **CORRECT** · PARAPHRASE
  - 답변: 한 프로세스 안에서는 힙과 코드가 함께 보입니다. 실행 위치와 레지스터, 호출 스택은 스레드별로 관리합니다. 개별 스택이라고 다른 스레드가 절대 접근할 수 없는 것은 아닙니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-01-K1, CS-01-K2
- `CS-01-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: 같은 프로세스의 스레드는 코드와 힙을 공유합니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: 각 스레드는 자신의 프로그램 카운터·레지스터 실행 상태와 스택을 갖는다. 스택은 논리적으로 개별이지만 같은 주소 공간의 접근 권한 격리는 아니다.
  - 제공 근거: CS-01-K1, CS-01-K2
- `CS-01-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: 스레드마다 힙이 분리되어 메모리가 격리되고 호출 스택 하나를 공동으로 사용합니다.
  - 판정 이유: 힙 공유와 스레드별 실행 상태를 모두 반대로 설명.
  - 제공 근거: CS-01-K1, CS-01-K2
- `CS-01-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: 한 프로세스 안에서는 힙과 코드가 함께 보입니다. 실행 위치와 레지스터, 호출 스택은 스레드별로 관리합니다. 개별 스택이라고 다른 스레드가 절대 접근할 수 없는 것은 아닙니다.
  - 판정 이유: 답변 내용은 정답 사례와 동일하지만 제공 근거에 CS-01-C2 설명이 없음. 외부 사전 지식·모범 답안으로 근거 누락을 대체하지 않고 검토 요청.
  - 제공 근거: CS-01-K1

## CS-02 · 교착상태와 잠금 순서

- 분야: CS · 난이도: INTERMEDIATE · 우선순위: P0
- 적용 조건: 운영체제 일반

**질문**

A가 L1을 잡고 L2를 기다리고, B가 L2를 잡고 L1을 기다립니다. 왜 멈추며 모든 작업에 같은 잠금 순서를 적용하면 어떤 조건을 제거하나요?

**모범 답안**

서로 상대가 가진 잠금을 기다려 순환 대기가 생기며 두 작업이 진행하지 못한다. 모든 관련 경로에 일관된 전역 잠금 순서를 적용하면 순환 대기를 차단한다. 한 경로에만 적용하면 충분하지 않다.

**필수 평가 기준**

- `CS-02-C1` · 가중치 0.50 · 서로 상대가 가진 잠금을 기다려 순환 대기가 생기며 두 작업이 진행하지 못한다.
- `CS-02-C2` · 가중치 0.50 · 모든 관련 경로에 일관된 전역 잠금 순서를 적용하면 순환 대기를 차단한다. 한 경로에만 적용하면 충분하지 않다.

**판정 사례**

- `CS-02-G01` · **CORRECT** · PARAPHRASE
  - 답변: 서로 잠금을 놓을 상대를 기다리므로 진행이 끊깁니다. 모든 코드가 L1 다음 L2 순서로 획득하면 이 잠금들 사이의 순환 대기를 만들 수 없습니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-02-K1, CS-02-K2
- `CS-02-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: 서로 상대가 가진 잠금을 기다리는 교착상태입니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: 모든 관련 경로에 일관된 전역 잠금 순서를 적용하면 순환 대기를 차단한다. 한 경로에만 적용하면 충분하지 않다.
  - 제공 근거: CS-02-K1, CS-02-K2
- `CS-02-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: CPU가 부족한 현상이므로 스레드를 더 만들면 해결됩니다. 잠금 획득 순서는 교착상태에 영향을 주지 않습니다.
  - 판정 이유: 자원 대기 관계를 CPU 부족으로 오인하고 순환 대기 예방 효과를 부정.
  - 제공 근거: CS-02-K1, CS-02-K2
- `CS-02-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: 서로 잠금을 놓을 상대를 기다리므로 진행이 끊깁니다. 모든 코드가 L1 다음 L2 순서로 획득하면 이 잠금들 사이의 순환 대기를 만들 수 없습니다.
  - 판정 이유: 답변 내용은 정답 사례와 동일하지만 제공 근거에 CS-02-C2 설명이 없음. 외부 사전 지식·모범 답안으로 근거 누락을 대체하지 않고 검토 요청.
  - 제공 근거: CS-02-K1

**꼬리 질문**

잠금 대기에 제한 시간을 주는 방법은 교착상태 예방과 어떻게 다른가요?

## CS-03 · 가상 메모리와 페이지 폴트

- 분야: CS · 난이도: INTERMEDIATE · 우선순위: P1
- 적용 조건: xv6 설명을 포함한 OS 원리; 구현별 처리 차이

**질문**

가상 주소를 쓰는 이유와 페이지 폴트가 항상 디스크 읽기를 의미하지 않는 이유를 설명하세요.

**모범 답안**

가상 주소를 물리 주소에 매핑하고 접근 권한을 검사해 프로세스별 주소 공간과 보호를 제공한다. 페이지 폴트는 지연 할당·복사 시 쓰기·잘못된 접근 등에서도 발생할 수 있어 디스크 적재가 항상 필요한 것은 아니다.

**필수 평가 기준**

- `CS-03-C1` · 가중치 0.50 · 가상 주소를 물리 주소에 매핑하고 접근 권한을 검사해 프로세스별 주소 공간과 보호를 제공한다.
- `CS-03-C2` · 가중치 0.50 · 페이지 폴트는 지연 할당·복사 시 쓰기·잘못된 접근 등에서도 발생할 수 있어 디스크 적재가 항상 필요한 것은 아니다.

**판정 사례**

- `CS-03-G01` · **CORRECT** · PARAPHRASE
  - 답변: 주소 변환과 권한 검사가 프로세스의 메모리 사용을 분리합니다. 폴트는 새 페이지 할당이나 COW 처리일 수도 있고, 잘못된 접근이면 오류 처리하므로 늘 디스크를 읽지는 않습니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-03-K1, CS-03-K2
- `CS-03-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: 가상 주소와 물리 주소를 연결하고 접근 권한으로 주소 공간을 보호합니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: 페이지 폴트는 지연 할당·복사 시 쓰기·잘못된 접근 등에서도 발생할 수 있어 디스크 적재가 항상 필요한 것은 아니다.
  - 제공 근거: CS-03-K1, CS-03-K2
- `CS-03-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: 가상 메모리는 디스크를 RAM처럼 쓰는 기능만 의미하며 페이지 폴트가 발생하면 반드시 디스크에서 페이지를 읽습니다.
  - 판정 이유: 주소 공간·보호 역할을 배제하고 페이지 폴트의 원인을 디스크 적재로 한정.
  - 제공 근거: CS-03-K1, CS-03-K2
- `CS-03-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: 주소 변환과 권한 검사가 프로세스의 메모리 사용을 분리합니다. 폴트는 새 페이지 할당이나 COW 처리일 수도 있고, 잘못된 접근이면 오류 처리하므로 늘 디스크를 읽지는 않습니다.
  - 판정 이유: 답변 내용은 정답 사례와 동일하지만 제공 근거에 CS-03-C2 설명이 없음. 외부 사전 지식·모범 답안으로 근거 누락을 대체하지 않고 검토 요청.

## CS-04 · TCP 바이트 스트림

- 분야: CS · 난이도: BASIC · 우선순위: P0
- 적용 조건: RFC 9293

**질문**

TCP에서 보내는 쪽이 두 번 write했다고 받는 쪽도 두 번 read로 같은 경계를 얻을까요? 보장과 메시지 구분 방법을 설명하세요.

**모범 답안**

TCP는 순서 있는 신뢰성 있는 바이트 스트림이며 애플리케이션의 write 경계를 보존하지 않는다. 애플리케이션 프로토콜에서 길이 필드·구분자·고정 길이 등으로 메시지 경계를 정의하고 부분 읽기를 처리한다.

**필수 평가 기준**

- `CS-04-C1` · 가중치 0.50 · TCP는 순서 있는 신뢰성 있는 바이트 스트림이며 애플리케이션의 write 경계를 보존하지 않는다.
- `CS-04-C2` · 가중치 0.50 · 애플리케이션 프로토콜에서 길이 필드·구분자·고정 길이 등으로 메시지 경계를 정의하고 부분 읽기를 처리한다.

**판정 사례**

- `CS-04-G01` · **CORRECT** · PARAPHRASE
  - 답변: TCP는 바이트 순서를 보장하지만 쓰기 횟수와 읽기 횟수는 맞지 않을 수 있습니다. 길이 접두어 등으로 프레임을 정하고 필요한 바이트가 모일 때까지 읽어야 합니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-04-K1, CS-04-K2
- `CS-04-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: TCP는 바이트 스트림이라 write 경계가 read 경계와 일치하지 않습니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: 애플리케이션 프로토콜에서 길이 필드·구분자·고정 길이 등으로 메시지 경계를 정의하고 부분 읽기를 처리한다.
  - 제공 근거: CS-04-K1, CS-04-K2
- `CS-04-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: TCP는 패킷마다 메시지를 보존하므로 write 두 번이면 read 두 번으로 정확히 받습니다. 별도 메시지 길이는 필요 없습니다.
  - 판정 이유: TCP의 스트림 성질을 메시지 경계 보장으로 오인.
  - 제공 근거: CS-04-K1, CS-04-K2
- `CS-04-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: TCP는 바이트 순서를 보장하지만 쓰기 횟수와 읽기 횟수는 맞지 않을 수 있습니다. 길이 접두어 등으로 프레임을 정하고 필요한 바이트가 모일 때까지 읽어야 합니다.

## CS-05 · HTTP 멱등성과 재시도

- 분야: CS · 난이도: INTERMEDIATE · 우선순위: P0
- 적용 조건: RFC 9110

**질문**

PUT 요청의 응답을 받지 못해 같은 요청을 다시 보냅니다. 멱등성이 의미하는 것과 응답이 같아야 하는지 설명하세요.

**모범 답안**

멱등성은 동일 요청을 여러 번 수행한 의도된 서버 효과가 한 번 수행한 효과와 같다는 의미다. 응답 상태·본문이나 로그 같은 부수 효과가 매번 같다는 뜻은 아니며 POST는 일반적으로 멱등성이 보장되지 않는다.

**필수 평가 기준**

- `CS-05-C1` · 가중치 0.50 · 멱등성은 동일 요청을 여러 번 수행한 의도된 서버 효과가 한 번 수행한 효과와 같다는 의미다.
- `CS-05-C2` · 가중치 0.50 · 응답 상태·본문이나 로그 같은 부수 효과가 매번 같다는 뜻은 아니며 POST는 일반적으로 멱등성이 보장되지 않는다.

**판정 사례**

- `CS-05-G01` · **CORRECT** · PARAPHRASE
  - 답변: 같은 리소스 상태를 설정하는 PUT은 반복해도 의도된 최종 효과가 같습니다. 첫 요청과 재시도의 응답 코드나 로그는 다를 수 있으며 POST 전체에 이 보장을 적용할 수는 없습니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-05-K1, CS-05-K2
- `CS-05-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: 동일 요청을 여러 번 보냈을 때 의도된 효과가 한 번 보낸 것과 같다는 의미입니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: 응답 상태·본문이나 로그 같은 부수 효과가 매번 같다는 뜻은 아니며 POST는 일반적으로 멱등성이 보장되지 않는다.
  - 제공 근거: CS-05-K1, CS-05-K2
- `CS-05-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: 멱등 요청은 서버 상태를 바꾸지 않으며 응답 코드와 응답 본문이 반드시 매번 같습니다.
  - 판정 이유: 멱등성을 안전성 및 응답 동일성과 혼동.
  - 제공 근거: CS-05-K1, CS-05-K2
- `CS-05-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: 같은 리소스 상태를 설정하는 PUT은 반복해도 의도된 최종 효과가 같습니다. 첫 요청과 재시도의 응답 코드나 로그는 다를 수 있으며 POST 전체에 이 보장을 적용할 수는 없습니다.
  - 판정 이유: 답변 내용은 정답 사례와 동일하지만 제공 근거에 CS-05-C2 설명이 없음. 외부 사전 지식·모범 답안으로 근거 누락을 대체하지 않고 검토 요청.
  - 제공 근거: CS-05-K1

## CS-06 · 격리 수준과 읽기 스냅샷

- 분야: CS · 난이도: INTERMEDIATE · 우선순위: P0
- 적용 조건: PostgreSQL 17; DB 제품 일반화 금지

**질문**

PostgreSQL 17의 Read Committed에서 한 트랜잭션이 같은 SELECT를 두 번 실행할 때 결과가 달라질 수 있나요? Repeatable Read와 비교하세요.

**모범 답안**

Read Committed의 각 명령은 그 명령 시작 시점의 스냅샷을 보므로 다른 트랜잭션의 중간 커밋에 따라 결과가 달라질 수 있다. Repeatable Read는 트랜잭션 제어문이 아닌 첫 명령 시점의 스냅샷을 후속 조회에도 사용한다. 자신의 변경은 보이며 동시 쓰기에는 재시도가 필요할 수 있다.

**필수 평가 기준**

- `CS-06-C1` · 가중치 0.50 · Read Committed의 각 명령은 그 명령 시작 시점의 스냅샷을 보므로 다른 트랜잭션의 중간 커밋에 따라 결과가 달라질 수 있다.
- `CS-06-C2` · 가중치 0.50 · Repeatable Read는 트랜잭션 제어문이 아닌 첫 명령 시점의 스냅샷을 후속 조회에도 사용한다. 자신의 변경은 보이며 동시 쓰기에는 재시도가 필요할 수 있다.

**판정 사례**

- `CS-06-G01` · **CORRECT** · PARAPHRASE
  - 답변: Read Committed는 SELECT마다 새로 커밋된 데이터를 볼 수 있습니다. Repeatable Read는 트랜잭션의 같은 스냅샷을 계속 보고 자기 변경도 반영하지만 동시 갱신 충돌 시 재시도할 수 있습니다.
  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.
  - 제공 근거: CS-06-K1, CS-06-K2
- `CS-06-G02` · **PARTIALLY_CORRECT** · OMISSION
  - 답변: Read Committed는 SELECT마다 스냅샷이 달라 다른 트랜잭션이 커밋하면 결과도 달라질 수 있습니다.
  - 판정 이유: 첫 기준 충족. 두 번째 기준 누락: Repeatable Read는 트랜잭션 제어문이 아닌 첫 명령 시점의 스냅샷을 후속 조회에도 사용한다. 자신의 변경은 보이며 동시 쓰기에는 재시도가 필요할 수 있다.
  - 제공 근거: CS-06-K1, CS-06-K2
- `CS-06-G03` · **INCORRECT** · FLUENT_WRONG
  - 답변: Read Committed는 트랜잭션 시작부터 모든 조회를 고정하고 Repeatable Read는 매 SELECT마다 새로운 커밋을 읽습니다.
  - 판정 이유: 두 격리 수준의 스냅샷 범위를 뒤바꿈.
  - 제공 근거: CS-06-K1, CS-06-K2
- `CS-06-G04` · **NEEDS_REVIEW** · INSUFFICIENT_EVIDENCE
  - 답변: Read Committed는 SELECT마다 새로 커밋된 데이터를 볼 수 있습니다. Repeatable Read는 트랜잭션의 같은 스냅샷을 계속 보고 자기 변경도 반영하지만 동시 갱신 충돌 시 재시도할 수 있습니다.
  - 판정 이유: 답변 내용은 정답 사례와 동일하지만 제공 근거에 CS-06-C2 설명이 없음. 외부 사전 지식·모범 답안으로 근거 누락을 대체하지 않고 검토 요청.
  - 제공 근거: CS-06-K1

**질문**

PostgreSQL 17 B-tree 인덱스 (tenant_id, created_at)가 있습니다. tenant_id 동등 조건과 created_at 범위 조건에 유리한 이유, created_at 조건만 있을 때의 한계를 설명하세요.

**모범 답안**

**필수 평가 기준**

- `CS-07-C1` · 가중치 0.50 · 선두 tenant_id 동등 조건 뒤의 created_at 범위 조건으로 연속된 인덱스 탐색 범위를 줄일 수 있다.

  - 답변: 복합 인덱스는 모든 열을 독립적으로 정렬하므로 열 순서가 무관하고 created_at만 검색해도 항상 같은 비용입니다.
  - 판정 이유: 복합 키의 정렬 순서와 선두 조건의 스캔 범위 축소 효과를 부정.

## JPA-02 · flush와 commit

**질문**

  - 판정 이유: 두 필수 기준을 의미상 충족. 정답과 다른 표현을 허용.

- `JPA-03-C1` · 가중치 0.50 · merge는 준영속 인스턴스의 상태를 같은 식별자의 관리 인스턴스에 복사하고 관리 인스턴스를 반환한다.

**판정 사례**
