## 문제와 판정이 동작하는 방식

```text
Source URL + 적용 버전
        ↓ 출처 확인·한국어 요약
KnowledgeDocument(DRAFT) → K1 / K2 근거 조각
        ↓                          ↓
Question + 필수 기준 C1 / C2     사례별 제공 근거 선택
        └──────────────┬───────────┘
                       ↓
             학습자 답변 + 제공 근거
                       ↓
          판정 결과 ↔ 기대 판정·판정 이유
```

- Question: 무엇을 묻고 어떤 필수 개념을 확인할지 소유
- KnowledgeDocument: 사실 근거와 적용 버전 소유
- Golden case: 답변·제공 근거·기대 판정이라는 평가 상황 소유
- 기준이 바뀐 경우: 해당 문제·근거·기대값을 함께 새 버전으로 관리. 과거 평가 결과에 현재 기준을 소급 적용하지 않음

### 사례 구성: 문제당 4개

| 유형 | 사례 수 | 답변 조건 | 근거 조건 | 기대값 |
|---|---:|---|---|---|
| PARAPHRASE | 50 | 필수 기준을 자기 말로 설명 | K1·K2 제공 | CORRECT / 100 |
| OMISSION | 50 | 첫 기준 설명, 두 번째 기준 누락 | K1·K2 제공 | PARTIALLY_CORRECT / 50 |
| FLUENT_WRONG | 50 | 해당 문제의 실제 오개념을 포함 | K1·K2 제공 | INCORRECT / 0 |
| INSUFFICIENT_EVIDENCE | 50 | PARAPHRASE와 같은 답변 | K1만 제공, C2 근거 부재 | NEEDS_REVIEW / null |

- 정답 문장과 문자열이 달라도 필수 의미가 같으면 정답
- 그럴듯한 표현이라도 핵심 모순이 있으면 오답
- “모르겠다”, 무관한 답변, 틀린 단정은 근거 부족과 별개. 채점기에 근거가 충분하면 학습자의 오답으로 판정
- G04는 답변을 바꾸지 않고 근거만 제거한 통제 실험. `referenceAnswer`나 모델 사전 지식으로 빠진 근거를 대체하면 이 사례의 평가 목적에 어긋남
- 모든 G04가 같은 근거 누락 패턴이라는 제한 존재. 버전 충돌·일부 잘못된 근거·검색 순서 변화는 후속 확장 대상

### 예: JAVA-04 volatile

```text
“다른 스레드의 쓰기를 관찰하는 규칙”        → C1
“count++ 전체의 원자성은 별도 장치 필요”    → C2

C1 + C2 설명, K1 + K2 제공 → 정답
C1만 설명, K1 + K2 제공   → 부분 정답
“volatile이 증가를 잠금”  → 오답
C1 + C2 설명, K1만 제공   → 검토 필요
```

## 프로젝트에 적용하는 순서

1. JSONL의 문자열 키를 Topic·Concept의 실제 DB ID와 매핑
2. 근거 요약을 `INTERNAL_SUMMARY` DRAFT로 등록하고 외부 참고 링크 연결
3. 독립 검수자가 공식 출처·버전·모범 답안·각 라벨을 대조. `reviewedBy`, `reviewedAt` 기록
4. 검수한 문서 공개 후 문제의 필수 Concept·가중치·모범 답안 확인 및 공개
5. 오프라인 평가에서는 사례별 지정된 근거 조각만 입력. 기대 라벨·이유는 평가기 입력에서 제외
6. 실제 검색을 포함한 전체 평가를 별도로 실행해 근거 검색 실패와 생성 판정 실패 분리

- 이 파일들은 관리자 API의 직접 요청 본문이나 자동 import 파일이 아님. Topic·Concept 숫자 ID, 등록 관리자, 실제 KnowledgeChunk ID 매핑 필요
- 외부 URL 여러 개와 자료별 상세 위치의 등록 방식: 현행 문서 API의 단일 sourceUrl 제약을 확인한 뒤 설명 본문 또는 출처별 문서로 매핑
- 근거 파일 DRAFT 상태: 오프라인 실험용으로 명시적으로 사용할 수 있으나 서비스 Retrieval에 바로 투입하지 않음
- 기존 OS TSV: 원본 보존. 이번 파일로 자동 교체하지 않음

## 기존 OS 세트 점검 결과

- 확인 위치: [os-golden-set.tsv](../../../src/test/resources/evaluation/os-golden-set.tsv)
- 반복 오답: 다른 주제에 동일한 “모든 자원과 권한을 항상 제한 없이 공유” 문장 사용
- 라벨 경계: 일부 OMISSION 답변이 정답 내용에 `한다.`만 덧붙인 형태. 개념 누락의 증거로 사용하기 어려움
- 근거 부족: 입력 근거 목록 없이 모호한 답변만 NEEDS_REVIEW로 지정한 사례
- 이번 개선: 문제별 오개념, 누락한 필수 기준 ID, 제공 근거 ID, 기대 판정 이유 명시
- 남은 한계: 이번 묶음도 같은 작성 주체가 문제·답변·라벨을 제작. 독립 정답의 확정본으로 간주 불가

## 검수·실측 계획과 실패 조건

- 사람 검수: 1차 판정과 근거 확인 후 불일치 사례 재판정. 핵심 판정의 독립성 확보
- 데이터 분리: 현재 전부 `split=UNASSIGNED`, `benchmarkEligible=false`. 개발·보류 세트 분리를 완료한 상태가 아님
- 누수 방지: 문제와 표현 변형은 같은 그룹. 관련 개념군까지 확인한 뒤 분리. 이 문서에 공개된 사례를 비밀 보류 세트라고 주장하지 않음
- 실사용 보완: 문체가 일정한 합성 답변만으로 출시 성능 추정 금지. 실제 학습자 답변, 짧은 답변, 오탈자, 무관한 답변, 공격성 답변 추가
- 실험 단위: 문제별 결과를 묶어 보고. 같은 문제의 네 사례를 완전히 독립된 사용자 표본으로 가정하지 않음
- 반복 측정: 모델·프롬프트·근거 버전·실행 설정 고정 후 여러 trial. 최초 값과 반복 일치율을 구분
- 보고 지표: 3종 판정 일치율, 이진 구분 정확도, 명백한 오답의 false-correct 비율, 검토 필요 판정, 근거 연결, schema 성공, 지연, 건당 비용
- 분모 명시: 현재 명백한 오답은 50개. 1개를 정답으로 오판하면 해당 표본 false-correct는 2%p 증가. 200개 전체를 분모로 희석하지 않음
- 수치 기준: [제품 명세의 초기 제안](../../product/spec.md)의 85%·90%·5% 등을 참조. 본 조사에서 새 출시 기준으로 확정하거나 달성했다고 표시하지 않음
